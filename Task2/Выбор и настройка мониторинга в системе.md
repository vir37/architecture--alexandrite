# Мотивация

Система является распределенной, состоит из нескольких сервисов. И уже сейчас наблюдаются проблемы, причину которых сложно выявить.
Вполне возможно, что какой-либо сервис перегружен. Метрики, особенно сгруппированные в одном представлении, дают наглядное понимание
"здоровья" системы. При наличии системы мониторинга причины проблем, вызывающих жалобы пользователей, могли быть легко определены (при условии,
что они вызваные чрезмерной нагрузкой на отдельные микросервисы) и быстро устранены (например, добавлением нового инстанса).
Еще одним плюсом внедрения мониторинга является возможность сбора и анализа так называемых бизнес-метрик: DUA, Retention, Conversion и др.
Анализ этих метрик может дать большее понимание о развитии бизнеса, натолкнуть на новые идеи и решения.

# Выбор подхода к мониторингу

Предлагаются следующие подходы к мониторингу системы:
1. USE для Shop DB, MES DB, 3D File Storage.
2. "Четыре золотых сигнала" для MES API, CRM API, Shop API.
3. RED для сервиса очереди сообщений RabbitMQ.

Предлагается следующий набор метрик:
1. **3D File Storage**:
  * "_Size of S3 storage"_ - метрика позволит своевременно реагировать при приближении размера хранилища к пороговому значению.
2. **MES DB**:
  * _"Memory Utilisation"_ - метрика показывает использование оперативной памяти: приближение показателя к верхнему пределу говорит о высокой загруженности сервиса.
  * _"Size of db"_ - метрика показывает размер дискового пространства, занимаемый базой данных: без регулярного обслуживания рост размера БД ведет к деградации производительности.
  * _"Number of connections"_ - метрика показывает интенсивность использования БД.
3. **Shop DB**:
  * _"Memory Utilisation"_ - метрика показывает использование оперативной памяти: приближение показателя к верхнему пределу говорит о высокой загруженности сервиса.
  * _"Size of db"_ - метрика показывает размер дискового пространства, занимаемый базой данных: без регулярного обслуживания рост размера БД ведет к деградации производительности.
  * _"Number of connections"_ - метрика показывает интенсивность использования БД.
4. **RabbitMQ**:
  * _"Number of message in flight"_ - метрика характеризует количество еще неподтвержденных сообщений: рост показателя свидетельствует о перегруженности очереди
  * _"Number of dead-letter-exchange letters"_ - метрика показывает количество проблемных сообщений (отвергнутых, недоставленных и т.д).
5. **MES API**:
  - _"CPU %"_ - метрика показывает процент загруженности CPU
  - _"Memory Utilisation"_ - метрика показывает использование оперативной памяти: приближение показателя к верхнему пределу говорит о высокой загруженности сервиса
  - _"Response time (latency)"_ - метрика показываем время обработки одного запроса (задержку): превышение показателя метрики пороговых значений ведет к формированию отрицательного пользовательского опыта
  - _"Number of requests (RPS) per user"_ - метрика показывает количество запросов в секунду, приходящееся на одного пользователя
  - _"Number of requests (RPS)"_ - метрика показывает общее количество запросов в секунду: превышение показателя установленнх пороговых значений может свидетельствовать о DDOS-атаке.
    Можно ввести флаг "IP-адрес клиента" для большего понимания входящего трафика
  - _"Number of HTTP 500"_ - метрика показывает количество отказов в обслуживании: превышение показателя установленных пороговых значений свидетельствует о проблемах внутри сервиса
  - _"Number of simultanious sessions"_ - метрика показывает количество одновременных сессий: высокое значение также может свидетельствовать о нездоровой активности

# План действий

1. Развернуть инстанс time-series базы данных.
2. Развернуть инстанс Prometheus.
3. Внедрить в сервисы, с которых планируется собирать метрики, агенты-экспортеры.
4. Сконфигурировать Prometheus на сбор данных с агентов-экспортеров.
5. Развернуть инстанс Graphana для визуализации метрик. Сконфигурировать подключение к Prometheus.
6. Настроить в Graphana удобное отображение необходдимых метрик.
7. Настроить в Graphana необходимые алерты.
