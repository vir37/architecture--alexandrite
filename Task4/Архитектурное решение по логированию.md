# Мотивация

Логирование - необходимая составляющая для повышения "наблюдаемости" системы. Наличие продуманных логов в каждом элементе системы позволит
быстро решать анализировать и находить причину возникающих инцидентов. Логи же уровня ERROR и FATAL (особенно при наличии алертинга) 
позволит оперативно реагировать на возникающие критические ситуации. Всё это вкупе будет формировать положительный пользовательский опыт.

Но надо понимать, что внедрение логирования добавит накладные расходы. Например, возрастет CPU % и Memory Utilisation, т.к. формирование логов - это дополнительная операция в бизнес-процессе.
Также в простом случае потребуется хранилище для сбора логов, в более сложном - система сбора, обработки и хранения.

От разработчиков потребуется внедрять в код вызовы, связанные с логированием.

Посколько полное внедрение предлагаемого решения трудозатратно, предлагается сначала настроить логирование для тех систем, 
которые отвечают за жизненный цикл заказа с момента создания до момента отправки покупателю. Это **Shop API**, **CRM API**, **MES API**.
Имеющиеся на данный момент проблемы с заказами предположительно связаны именно с этими элементами системы.

# Предлагаемое решение

В качестве решение предлагается внедрить стек ELK. Для этого необходимо будет развернуть отдельный инстанс Elasticsearch (для агрегации и хранения логов),
отдельный инстанс Kibana (для предоставления удобного интерфейса просмотра и анализа логов).
Для сбора и отправки логов в ELK элементы (сервисы) системы необходимо будет доработать для формирования сруктурированных логов. Также потребуется развернуть
не менее одного инстанса Filebeat для считывания и преобразования логов сервисов с последующей отправкой их в ELK.

Для авторизации пользователей, допущенных к работе с данными лога, хорошим решением будет развернуть инстанс Keycloak (о нем же говорилось в предложение решения для мониторинга и трейсинга).
Будет удобно управлять группами пользователей и сквозной аутентификацией.

Доступ к данным должны иметь как разработчики, так и DevOps-инженеры. Доступа менеджерам должен отсутствать, так как описанная выше модель логов не содержит полезной
для них информации. 

Имеет смысл разделить индексы в Elasticsearch  по уровням логирования: INFO и WARNING в одном индексе, прочие уровни в другом. В отдельный индекс стоит выделить индекс 
для логирования действий пользователя (вход, выход, ошибки аутентификации). Индекс для уровня INFO и WARNING достаточно хранить не более месяца. Остальные дольше.

Политику управления индексами стоит настроить так, чтобы размер шарда не превышал 50ГБ. На начальном этапе предполагается, что один индекс состоит из одного шарда.
Это оптимизирует расходы на старте, т.к. отдельный шард стоит хранить на отдельной ноде.

# Мероприятия для превращения системы сбора логов в систему анализа логов

Необходимо настроить алертинги.
Обязательными для оповещения являются системные события уровня FATAL и ERROR, так как свидетельствуют о проблемах системного уровня и требуют
безотлагательного вмешательства.

В Kibana необходимо настроит специальны представления для отображения необычных процессов системы.
1) Количество попыток неправильного ввода логина/пароля превышает пороговое значени
2) Количество новых закалов в единицу времени превышает пороговое значение в определенное число раз
3) Количество ошибок работы с БД превышает пороговое значение.
