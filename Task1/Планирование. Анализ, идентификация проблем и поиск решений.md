# Существующие и потенциальные проблемы

1. Сервис API MES занимается как обслуживанием производства заказа, так и рассчетом стоимости производства заказа по 3D-модели. 
 Причем расчет может оказаться довольно затратным в плане вычислительных мощностей.

2. Логирование реализовано на минимальном уровне (если вообще реализовано).

3. Существующий мониторинг системы не охватывает все критически важные элементы системы. Что затрудняет выявление перегруженных мест.

4. Поскольку система распределенная, необходимо внедрение трейсинга для эффективного и быстрого выявления мест, вызывающих проблемы.

5. Отсутствует кэширование данных, используемых в интерфейсах пользователей. Это в свою очередь увеличивает нагрузку на БД.

6. Практически не используются практики CI/CD, что тормозит выход новых релизов. Частые релизы способствуют быстрому получению обратной связи
 от пользователей по доработкам продукта, что помогает быстрее вносить исправления.
 
 
# Инициативы по улучшению в порядке приоритета

1. Внедрить мониторинг. Мониторинг позволит получать оперативную информацию о состоянии системы. Кроме того определенный набор метрик (бизнес-метрик)
 может дать дополнительную информацию о развитие бизнеса, потребностях пользователей системы, натолкнуть на новые решения. Визуализация метрик со всех участков системы
 в одном удобном интерфейсе облегчит наблюдение за системой, а внедрение алертинга позволит оперативно реагировать на возникающие инциденты.

2. Внедрить системы логирования. Сбор и агрегация логов с различных участков системы позволит получать куда более детальную информацию о процессах, происходящих в системе.
 Это позволит быстрее решать возникающие проблемы.

3. Внедрить трейсинг. Поскольку в настоящий момент уже имеется довольно большой объем жалоб клиентов (и даже случаи потери клиентов),
 необходимо как можно быстрее разобраться с проблемой просроченных заказов. Раз дело не в мощностях производства, значит возникают
 какие-то невалидные ситуации с заказами внутри системы.
 
3. Предположительно сервис MES не справляется с нагрузкой, т.к. расчет стоимости производства заказа по 3D-модели потенциально ресурсоемкая операция.
 Предлагается запустить еще один инстанс сервиса MES только под функционал расчета стоимости производства и через API Gateway разделить потоки
 запросов к MES API на разные инстансы в зависимости от задач. В будущем (т.к. у нас имеется кодовая база MES) желательно разделить этот сервис
 на два: сервис расчета стоимости производства по 3D-модели и сервис обеспечения жизненного цикла производства изделия.

4. Также возможно, что сервисы, предоставляющие API для внешних пользователей (MES API, Shop API), испытывают перегрузки в связи с большим потоком запросов (легитимных или не очень).
 Особенно это относится к MES API (хотя это можно было бы понять по уже настроенным метрикам Яндекс). В этом случае стоит рассмотреть внедрение Rate-Limiting, что позволит управлять нагрузко на API.
 
5. Чтобы обеспечить комфорт работы операторов сервиса MES (а значит повысить качество обслуживание клиентов) предлагается внедрить кэширование
 данных для этого сервиса. Поскольку операторам важна актуальность информации по заказам, кэширование лучше внедрять серверное.
 
6. Внедрить практики CI/CD. Инженер QA имеет определенный опыт реализации автоматических тестов. Необходимо с ручного тестирования переходить
 на автоматическое. Также необходимо настроить пайплайны автоматической сборки и развертывания системы в release-окружении и в продакшн версию.
 


В конечно итоге должна повыситься наблюдаемость системы за счет внедрения трейсинга и мониторига с логированием;
должна улучшиться масштабируемость за разделения на дополнительные микросервисы системы MES;
должна улучшиться отзывчивость системы за счет внедрения кэширования;
должно повыситься качество разработки за счет внедрения автоматических тестов, а также уменьшения периодичности релизов в связи с полноценным
использованием практик CI/CD.
